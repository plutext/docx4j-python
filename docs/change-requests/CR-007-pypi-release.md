# CR-007: Publishing to PyPI --- the fork first, then the package

**Status:** Proposed 2026-09-20; **the ten open questions decided 2026-09-20, every
recommendation accepted** (section 8 records each as decided). Nothing implemented. Phase A (the
fork's release) is ready to start; Phase B (this package) follows it and is not started until
Phase A's distribution resolves from PyPI. The outward-facing steps --- pushes, the GitHub
repository rename, the PyPI publisher settings, the releases themselves --- are the user's, and
are listed as such. **The rename is done** (2026-09-20, `plutext/docx4j-xsdata`; section 3.6's
housekeeping with it); the rest waits.

Companion: the xsdata fork's `docs/fork/REBASING.md` (its "Publishing" section already fixes the
tag scheme this CR adopts) and docx4j-core-ts's `RELEASING.md` (the release procedure this CR
copies, npm for PyPI).

## 1. Why

Everything the package promises is built and measured: the object model (CR-001, Phases A to C,
refreshed to docx4j `58cce65a8` in section 14.10), the engine (CR-002, Phases A and B, zero
differences on all 45 parity goldens), and the whole content API with the python-docx facade
(CR-003, every phase). It is used from one checkout, by one person and by agents, through two
git-ignored virtual environments. The point of a Python analogue of docx4j is that
`pip install` gets it, and `docs/python_ecosystem.md` in the portfolio positions it against
python-docx on exactly that footing. Nothing in the code waits on a release; the release waits on
packaging, which is what this CR is.

A release is also a promise. A version number says how much of the surface may move, so the CR
says which parts are stable (section 4.3) rather than leaving the reader to guess from `0.x`.

## 2. The blocker: the dependency

Every generated module imports `docx4j_xsdata`. `pyproject.toml` depends on
`docx4j-xsdata[lxml]==26.2`, which exists in exactly one place, installed editable into
`.venv-fork` from `~/git/docx4j-xsdata`. On PyPI, `docx4j-xsdata`, `docx4j`, `docx4j-py` and
`docx4j-python` are all unregistered (checked 2026-09-20). A package whose one dependency cannot
be resolved is worse than no package, so the fork is published first, and this package is never
published against an unreleased fork --- docx4j-core-ts's rule for
`@docx4j/generated-objects-ts`, copied.

The fork's state on 2026-09-20: branch `docx4j` on upstream tag `v26.2`, 16 commits ahead of
`origin/docx4j` (last pushed 2026-09-14; the two generator fixes of CR-001 section 14.10 are
among the unpushed), with `pyproject.toml` already carrying the distribution name, the MIT
licence, the fork README and a five-version CI matrix (3.10 to 3.14, `tests.yml`). Three things are
not release-ready: `__version__` is `"26.2"`, upstream's own number; the project URLs name
`github.com/plutext/docx4j-xsdata` while the remote is `github.com/plutext/xsdata`; and there is
no publishing workflow (upstream's was dropped in the rename, `CHANGES.md` stage 1).

## 3. Phase A: the fork's release

### 3.1 Version

`26.2.1`, tagged `docx4j-v26.2.1`, exactly the scheme `REBASING.md` fixes: `<upstream tag>.<fork
release>`, the fork release counting up from 1 and resetting when the base moves. Upstream's
versions are two components (`24.9`, `25.4`, `25.7`, `26.1`, `26.2`), so a three-component number
never collides with an upstream release and reads as what it is: upstream `26.2` plus fork release
1. The alternatives are worse. `0.26.2` hides the base, which is the whole point of the naming.
`26.2.post1` is PEP 440's spelling for a packaging-only re-release and this is a feature fork.
`26.2+docx4j.1` is a local version label, which PyPI rejects.

`__version__` moves in an ordinary feature commit on `docx4j`, replayed by each rebase like the
others; the bump is the last commit before the tag. Nothing generated changes when it moves: the
generated tree carries no version header (`grep -r 'generated by' docx4j_py` finds nothing; the
config suppresses it), and `GeneratorConfig.read` overwrites the config file's `version="26.2"`
attribute rather than checking it.

### 3.2 Metadata

- `[project.urls]`: `Homepage` and `Source` point at the repository that exists. The
  recommendation (open question 7) is to rename the GitHub repository from `plutext/xsdata` to
  `plutext/docx4j-xsdata`, since the distribution, the README, the tag scheme and the URLs already
  say `docx4j-xsdata` and GitHub redirects the old name; failing that, the URLs change.
- `authors` stays upstream's author (the MIT notice requires the copyright to survive and the
  metadata is where a reader looks); `maintainers` gains Plutext.
- `classifiers`: `Development Status :: 5 - Production/Stable` is upstream's claim and stays ---
  the fork is upstream plus a rename and eight measured features, not a new library.
- `readme`, `license`, `license-files`, `keywords`, `requires-python >=3.10`, the extras, the
  console script: unchanged.
- `CHANGES.md` (`docs/fork/`) gains "Stage 8 --- publishing": the version, the tag, the workflow.

### 3.3 Publishing mechanism

Trusted publishing from GitHub Actions, no token stored anywhere, as docx4j-core-ts publishes to
npm. `.github/workflows/publish.yml` runs on a GitHub **release** (`types: [published]`), checks
that the release tag matches `__version__` (`docx4j-v26.2.1` against `26.2.1`), builds the sdist
and wheel with `python -m build`, and publishes with `pypa/gh-action-pypi-publish` under
`permissions: id-token: write`. PyPI's **pending publisher** feature registers a trusted publisher
for a project name that does not exist yet, so the first release can go through the workflow
too and no API token is ever created (open question 6); the user configures it on pypi.org
(organisation `plutext`, repository as renamed, workflow `publish.yml`, no environment).

A dry run first: the same workflow with `repository-url: https://test.pypi.org/legacy/` on a
`workflow_dispatch`, so the name, the metadata rendering and the wheel are seen on TestPyPI
before the name is taken on PyPI.

### 3.4 What ships

The wheel is `docx4j_xsdata*` (`[tool.setuptools.packages.find]`), the sdist is upstream's
`MANIFEST.in` (tests and docs included). Nothing to change. `python -m build` and
`twine check dist/*` are run once by hand before the first release and recorded.

### 3.5 Gates

1. The fork's own suite: `PATH=.venv-fork/bin:$PATH python -m pytest tests -o addopts="" …`
   (1,556 passed on 2026-09-20).
2. **The consumer test**, which the fork's suite cannot stand in for: the built wheel installed
   into a clean 3.12 virtual environment, this repository's `docx4j_py` importable against it,
   `codegen/generate.sh --check` byte identical, and the fast suite green. The fork's features
   exist for this package, so this package is the acceptance test.
3. `twine check` clean; TestPyPI shows the README rendered.

### 3.6 The repository rename, first

Renaming `plutext/xsdata` to `plutext/docx4j-xsdata` on GitHub is independent of everything
else in this CR and is the one step that is better done before Phase A starts than after: the
fork's `pyproject.toml` URLs, README, tag scheme and this CR already say `docx4j-xsdata`, and a
trusted publisher is registered against a repository name, so the pending publisher of section
3.3 should be created against the final one. GitHub redirects the old name for clones, fetches
and links, so nothing breaks in the meantime. **Done 2026-09-20**, with its housekeeping the same
day (fork commit on `docx4j`, CR-001 section 4 here):

- `git remote set-url origin https://github.com/plutext/docx4j-xsdata.git` in the local
  checkout (the redirect would carry it, but a remote should say where it points);
- `docs/fork/REBASING.md` (three mentions of `plutext/xsdata`: the remotes table, "The fork
  lives at", the `origin` row) and this repository's CR-001 section 4 ("**Repository:**
  `plutext/xsdata`");
- "Sync fork" and the upstream remote are unaffected --- the rename does not change that the
  repository is a GitHub fork of `tefra/xsdata`.

A fork on GitHub keeps its fork relationship through a rename; upstream pull requests still
default to `tefra/xsdata` as the base, which `REBASING.md` already warns about.

## 4. Phase B: this package's release

### 4.1 Name and version

**Distribution `docx4j`, import `docx4j_py`, version `0.1.0`** (open question 1 has the
alternative). `docx4j` is the brand that fifteen years of documentation and examples carry, it
is free on PyPI today and will not be forever, and `pip install docx4j` is what a docx4j user
types first. The import name stays `docx4j_py`: a rename would touch every generated module,
every test and every CR, and `docx4j` as a top-level Python package would shadow nothing but
would invite `import docx4j` confusion with Java-side names. `python-docx` / `docx` and
`beautifulsoup4` / `bs4` are the precedent for a distribution and an import named differently.

`0.1.0` is what docx4j-core-ts released first; the two engines are one design and their numbers
should read across. `0.x` says the surface may move in a minor version; section 4.3 says which
parts are expected to and which are not.

### 4.2 Metadata

`pyproject.toml`'s `[project]` table, rewritten:

- `description`: one sentence, the real one --- "docx4j for Python: ECMA-376 WordprocessingML as
  typed objects, the Open Packaging engine, and a content API in Office JS's vocabulary with a
  python-docx facade". The current "Feasibility experiment" line is what PyPI would show.
- `readme`: a **separate, short `docs/pypi-readme.md`** (open question 5), about 150 lines: what
  it is, install, the first example, the agent loop, the facade, what is and is not supported
  (WordprocessingML; PML and SML are CR-001 Phase D and CR-002 Phase C), links to the repository,
  the CRs and docx4j. The 969-line `README.md` stays the repository's front page. A test keeps
  the short readme's examples executing (section 4.5).
- `dependencies`: `docx4j-xsdata[lxml]>=26.2.1,<26.3` and `markdown-it-py>=3.0`. Not `==`: a fork
  release within the same upstream base is additive by `REBASING.md`'s rule, and a consumer who
  installs a later `26.2.n` for a fix should not be refused. The upper bound is where the base
  moves and the bindings are regenerated (open question 3).
- `requires-python = ">=3.12"`, as now; CI proves 3.12, 3.13 and 3.14 (section 4.4). The fork
  floors at 3.10, but this package has only ever run on 3.14 and the point of the floor is the
  versions actually tested, not the widest one the syntax permits (open question 4).
- `classifiers`: `Development Status :: 3 - Alpha`, `License :: OSI Approved :: Apache Software
  License` is **not** listed (PEP 639: the SPDX `license` field replaces it and hatchling 1.27
  rejects the pair), `Programming Language :: Python :: 3.12` / `3.13` / `3.14`,
  `Topic :: Office/Business :: Office Suites`, `Topic :: Text Processing :: Markup :: XML`,
  `Typing :: Typed` once a `py.typed` marker is added to `docx4j_py/` (it is a slotted-dataclass
  model with annotations throughout; the marker is one empty file, kept by `KEEP`).
- `keywords`: `docx`, `docx4j`, `wordprocessingml`, `ooxml`, `office-open-xml`, `python-docx`,
  `mcp`, `agents`.
- `urls`: `Homepage` (the repository), `Source`, `Changelog` (`CHANGELOG.md`, section 4.6),
  `docx4j` (`https://www.docx4java.org`), `Issues`.
- `authors`: Plutext Pty Ltd.

### 4.3 What the version promises

Stated in the PyPI readme and `CHANGELOG.md`, so `0.1.0` is not read as "anything may change":

| Surface | Stability in `0.x` |
|---|---|
| `docx4j_py.load`, `create_package`, `WordprocessingMLPackage`, the parts, `PartStore` / `PartSink` | Stable: docx4j's names and behaviour, departures recorded in CR-002 section 12.3 |
| The content API (`Body`, `Paragraph`, `Range`, `Table`, …, the agent surface, markdown) | Stable in shape: Office JS's vocabulary is borrowed, not invented; a member may be added in a minor, none renamed |
| `docx4j_py.docx`, the python-docx facade | Stable: its promise is `tests/python_docx_subset.json`, 305 of 312 members |
| The generated model (`docx4j_py.wml` and the rest, `el`) | Regenerates with the schema; class and field names are docx4j's and do not move, but a schema refresh adds fields and classes in a minor (section 14.10 added five classes and three `el` entries) |
| `docx4j_py.model` (resolver, `StyleUtil`, fonts, numbering) | Stable: docx4j's, zero differences on the goldens |
| Anything under `codegen/`, `scripts/`, `baseline/` | Not shipped |

### 4.4 CI

This repository has no CI. Two workflows, modelled on docx4j-core-ts's `test.yml` and
`push-to-npm.yml`:

- `test.yml`, on push and pull request to `main`: a matrix over 3.12, 3.13 and 3.14 installing
  `.[dev]` from PyPI (the fork **from PyPI**, not a checkout, which is what a consumer gets) and
  running `pytest -m "not slow"`; one job on 3.14 running the full suite (the corpus round trip
  and the timings; the goldens skip because `../docx4j-core-ts` is absent, as they are designed
  to) and `codegen/generate.sh --check`. The timing tests' thresholds are checkout-machine
  numbers; if a runner fails them, they are marked `slow` and excluded from the matrix rather
  than loosened.
- `publish.yml`, on a GitHub release: the tag-equals-version check (`v0.1.0` against
  `pyproject.toml`), `python -m build`, `twine check`, `pypa/gh-action-pypi-publish` with trusted
  publishing; TestPyPI on `workflow_dispatch`.

### 4.5 Gates

1. Full suite green on the checkout and on CI's matrix.
2. `codegen/generate.sh --check` byte identical against the fork **as installed from PyPI**.
3. **The wheel, not the checkout**: `python -m build`, `unzip -l` reviewed against section 4.7,
   the wheel installed into a clean 3.12 virtual environment with nothing else, and a smoke script
   run from a directory outside the repository (`load` a corpus document, edit through the content
   API and the facade, `save`, `warm_up()`), so that a missing resource file or an import that
   only works from the checkout is caught.
4. `scripts/acceptance.py` run **from that installed wheel** and the eleven artefacts opened in
   Word by the user, recorded in `tests/README.md` as every check is. Packaging is a marshalling
   input in the sense the rule cares about --- a resource missing from the wheel changes what is
   written --- so the check is not waived for dates-only differences this once.
5. `tests/test_readme.py`: every ```` ```python ```` fence in `docs/pypi-readme.md` executed in
   order in a temporary directory over `samples/`, so the examples on PyPI are true (the fences in
   `README.md` are executed the same way where they are self-contained; the ones that are
   fragments are marked with an HTML comment the test skips). `README.md`'s 37 fences have been
   run by hand at each phase; this makes it a test.
6. TestPyPI first, the rendered page read, then PyPI.

### 4.6 Documents

- `RELEASING.md` at the root, docx4j-core-ts's structure: publishing target and trusted-publisher
  settings, the dependency rule (never against an unreleased fork; raising the fork bound), first
  release, steps, what ships.
- `CHANGELOG.md`, starting at `0.1.0`, one paragraph per CR summarising what the release contains,
  each linking the CR's implementation-notes section rather than repeating it.
- `README.md`: the status paragraph says WordprocessingML only, names PML and SML as CR-001 Phase
  D and CR-002 Phase C, and links `docs/pypi-readme.md`; the `Licence` section gains the NOTICE
  (section 4.7).
- `NOTICE`: Apache-2.0 attribution for what the wheel carries from elsewhere ---
  `resources/KnownStyles.xml`, the default styles, numbering and font table under
  `resources/openpackaging/`, the three Office theme parts and the substitution tables under
  `resources/fonts/` (docx4j's, Apache-2.0, as `scripts/generate_fonts.py` records), and the
  fork's MIT runtime as a dependency. The schemas are ECMA-376's and are not in the wheel.

### 4.7 What ships

The wheel: `docx4j_py/` --- 238 modules, `resources/` (376 KB: the warm-up parts, `KnownStyles.xml`,
the default parts, `fonts/`), `py.typed`, `LICENSE`, `NOTICE`. hatchling's `packages =
["docx4j_py"]` already includes the resource files and respects `.gitignore` for `__pycache__`;
the gate is `unzip -l`, not trust. Expected size: the source is 13 MB, 148,000 lines, so a
compressed wheel of two to three megabytes --- large for a pure-Python wheel and worth stating in
the readme with the reason (the whole of WordprocessingML as typed classes, imported in 0.6 s).

The sdist: the wheel's contents plus `tests/`, `samples/` (docx4j's fixtures, Apache-2.0, 1.4 MB),
`schemas/`, `codegen/`, `scripts/`, `docs/`, `pyproject.toml` and the READMEs, so that
`pip download --no-binary` gets something whose suite runs (open question 9). Not `baseline/`,
`out/`, `.venv*`, `.claude/`.

Nothing in the model, the engine or the content API changes for the release. The version is
metadata.

## 6. Tests

Section 3.5 and section 4.5 are the gates; the only new test file is `tests/test_readme.py`.
The consumer test of 3.5 point 2 and the clean-environment install of 4.5 point 3 are scripted
(`scripts/release_check.sh`: build both wheels, make the venv, install, run the smoke script,

check, not a memory of what was done last time.

## 8. Open questions (decided 2026-09-20: every recommendation accepted)

1. **Distribution name.** *Decided: `docx4j`.* `docx4j` (recommended: the brand, free today, what a docx4j user types)
   or `docx4j-py` (matches the import name and the current `pyproject.toml`; no "why is the
   import different" question). Whichever is not taken should not be squatted with a placeholder
   --- PyPI removes those.
2. **Fork version.** *Decided: `26.2.1`.* `26.2.1` under `REBASING.md`'s scheme (recommended) or `0.26.2`.
3. **Dependency bound.** *Decided: `>=26.2.1,<26.3`.* `>=26.2.1,<26.3` (recommended) or `==26.2.1`. The exact pin is safer
   for the generated bindings and worse for a consumer who needs a fork fix; the range trusts
   the rebase rule that a fork release on the same base is additive.
4. **Python floor.** *Decided: `>=3.12`.* `>=3.12`, the tested versions (recommended), or `>=3.10` to match the fork.
   Widening is one CI matrix change later; narrowing after a release is a breaking change.
5. **PyPI readme.** *Decided: a separate `docs/pypi-readme.md`, tested.* A separate short `docs/pypi-readme.md` with its own executing test
   (recommended) or `README.md` as it is (969 lines, the agents section, the layout section).
6. **First publish.** *Decided: through `publish.yml` with a pending publisher.* Through `publish.yml` with a PyPI pending publisher, so no token ever
   exists (recommended), or by hand with `twine` and an account token as core-ts's first npm
   release was. Either way TestPyPI first.
7. **The fork's GitHub repository name.** *Decided: rename; the user does it before Phase A (section 3.6).* Rename `plutext/xsdata` to `plutext/docx4j-xsdata`
   (recommended: everything else already says so, GitHub redirects) or change the URLs to the
   current name.
8. **The readme test.** *Decided: `tests/test_readme.py`.* `tests/test_readme.py` executing the fences (recommended) or a step in
   `RELEASING.md` run by hand.
9. **The sdist.** *Decided: with `tests/`, `samples/`, `schemas/` and `codegen/`.* With `tests/`, `samples/`, `schemas/` and `codegen/` so its suite runs
   (recommended, about 3 MB more) or the wheel's contents only.
10. **`Typing :: Typed`.** *Decided: `py.typed` in `0.1.0`.* Add `py.typed` and claim it (recommended: the annotations are
    complete, and a facade user with mypy gets the model's types) or leave it for `0.2` after a
    mypy run over `docx4j_py/` has been done, which it has not.
