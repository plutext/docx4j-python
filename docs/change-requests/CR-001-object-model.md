## 1. Summary

docx4j-python is the Python analogue of docx4j: the whole of ECMA-376 as typed objects, with an
engine (Open Packaging, parts, load and save) written by hand over them. This CR is the object
model half: how the classes are generated, what every generated class carries at runtime, and the
constructors and helpers a user (or an agent) builds trees with. The engine is CR-002 and the
content API is CR-003; both follow the corresponding docx4j-core-ts CRs closely and are not
repeated here.

The generator is [xsdata](https://xsdata.readthedocs.io). The experiment of 2026-09-12
(`REPORT.md`) showed that unmodified xsdata already round-trips real Word documents with **no
structural loss**: 50 parts from 12 documents, not one element dropped, reordered or changed;
choice-group order, w14 and w15 markup, `mc:AlternateContent`, text and `xml:space` all intact. It
also showed six things the generator and runtime get wrong for OOXML that configuration, schema
patches and runtime hooks cannot fully cover (section 3). Decision (2026-09-12): **maintain a
fork of xsdata**, keep its delta small, upstream what is generic, and publish the runtime under a
different name.

Design rules, carried over from docx4j:

- **Round-trip fidelity is the core promise.** Anything the schema does not know must survive, or
  its loss must be reported. Lenient parsing that silently discards content is not acceptable.
- **Schema-invalid but real documents load.** Word and JAXB accept a `w:tbl` without `w:tblGrid`;
  so must this. Nothing the schema marks required may be a mandatory constructor argument.
- **Every object knows its parent**, as docx4j's `Child` interface gives, and a subtree can be
  copied without copying the document.
- **Names follow docx4j** where the Java reads well in Python, so that docx4j documentation,
  examples and agents' training material carry over; departures are recorded (section 6).

## 2. Non-goals

The engine (CR-002), the content API (CR-003), JSON interchange with docx4j-ts (the Jsonix
layout; xsdata's JSON uses Python field names and a mapping layer would be its own CR),
PresentationML and SpreadsheetML beyond generating their packages, performance work on the
serialiser beyond what section 8 accepts, and schema validation.

## 4. The fork

- **Repository:** `plutext/xsdata`, branched from the 26.2 tag, rebased onto upstream tags as
  they appear. Upstream released ten times in 2024, twice in 2025 and twice so far in 2026, and
  has one maintainer with about 1,430 commits to the next contributor's seven; tracking it is
  cheap and owning the fork is also insurance.
- **Two halves, two policies.** The *generator* (`xsdata.codegen`, `xsdata.cli`) is a build-time
  tool that only this project runs; it may diverge freely, and the OOXML semantics (everything
  optional, defaults on read, `ChildList`) live there as configuration flags that default to
  upstream behaviour so the fork can still generate ordinary bindings. The *runtime*
  (`xsdata.formats.dataclass`, parsers, serialisers, `XmlContext`) is what every user installs;
  changes there are kept to the minimum that subclassing cannot reach.
- **Naming.** The runtime is published as the distribution `docx4j-xsdata` with the import
  package `docx4j_xsdata`, and the console script is renamed, so it coexists in one environment
  with upstream `xsdata`. Upstream has about 3.2 million PyPI downloads a month against 450
  GitHub stars: it is a transitive dependency of something widely installed, and a clash cannot
  be predicted from the AI-application audience alone. Generated code imports runtime types from
  `docx4j_xsdata`. The upstream plugin ecosystem (xsdata-pydantic, xsdata-attrs, both at 24.5;
  xsdata-plantuml) does not apply to the renamed package and is not wanted.
- **Upstream first** for anything generic: the circular-import bug, the inner-class bug, a
  skipped-content report. Each accepted patch leaves the fork. Reports are deferred until the
  fork's fixes exist (decided 2026-09-12); the list is `docs/UPSTREAM.md`.
- **Not the fork's business:** the schema patches (section 7), prefix and `mc:Ignorable`
  handling, MCE preprocessing. Those are OOXML knowledge and live in this repository, as docx4j
  keeps them in `org.docx4j`.

## 5. What every generated class carries: `Child`

The generator's extension config adds one base class to every generated dataclass. It is the
analogue of docx4j's `Child` interface plus what `XmlUtils.deepCopy` gives.

```python
class Child:
    __slots__ = ("parent",)          # not a dataclass field: absent from __init__, __eq__, repr, serialisation

    def __deepcopy__(self, memo):     # copies the subtree; the copy's parent is None until inserted
    def get_parent(self) -> Child | None
    def set_parent(self, parent) -> None
```

- `parent` is a slot, not a field, so no `XmlType.IGNORE` metadata is needed and equality between
  a parsed and a constructed tree is unaffected. `--slots` stays on; the slot is declared on the
  base class, which `dataclass(slots=True)` respects.
- **Wiring on parse:** a post-order walk after `XmlParser` returns, driven by the class metadata
  (`XmlContext` knows every element field), so it is generic and needs no generated code. A
  parser hook in the fork is an optimisation for later; the walk costs one pass and is measured
  in section 8.
- **Wiring on mutation:** `ChildList`, a `list` subclass whose `append`, `insert`, `extend`,
  `__setitem__` and slice assignment set the item's parent to the owner, as `ArrayListDocx4j`
  does; the fork emits `default_factory=ChildList` (bound to the owner in `__post_init__`) for
  every list field. Single-valued fields are wired by the walk and by the object factory
  (section 6); a user assigning `p.p_pr = ppr` directly gets no parent until the next
  `link_parents(root)`, which is the `deepCopy(value, parent)` idiom of docx4j-core-ts CR-002.
- **Deep copy:** `copy.deepcopy` on the generated slotted classes works as generated (verified
  2026-09-12: a paragraph with a run with text copies and compares equal). With a parent slot it
  would follow the pointer and copy the document; `Child.__deepcopy__` copies fields only, then
  relinks the copy's descendants. `deep_copy(obj, parent=None)` is the public name.

## 6. Names, layout and the object factory

### 6.1 Layout and names

- **One package per namespace,** as docx4j has one Java package per namespace: `docx4j_py.wml`,
  `docx4j_py.dml`, `docx4j_py.dml.wordprocessing_drawing`, `docx4j_py.math`, `docx4j_py.mce`,
  `docx4j_py.relationships`, `docx4j_py.vml`, `docx4j_py.w14`, `docx4j_py.w15`, and so on. This
  requires the `namespaces` structure style, hence the circular-import fix in the fork.
  Cross-namespace cycles (WML embeds DML, DML embeds WML through `a:graphicData`) are broken with
  `from __future__ import annotations` and `TYPE_CHECKING` imports in the generated modules.
- **Class names follow docx4j** through the fork config's class-name substitutions: `P`, `R`,
  `Text` (for `w:t`), `PPr`, `RPr`, `Body`, `Document`, `Tbl`, `Tr`, `Tc`, `Style`, `Styles`,
  `CTSettings`, `CTShd`, and the rest as `org.docx4j.wml` has them (a table generated from
  docx4j's `ObjectFactory` and committed under `codegen/names/`). Element-specific subclasses
  that xsdata creates where one type serves several element names (`Ins1`, `Del1` today) take
  the element name, `RunIns`, `RunDel`, as docx4j names them. Local element types that xsdata
  nests (`R.T`, 2,102 nested classes in the current output) are unnested (`UnnestClasses`) and
  named by the same table. Field names are `snake_case` of the schema name (`p_pr`, `r_pr`,
  `content`), the one systematic departure from Java's `getPPr()`.
- **Enums** keep xsdata's form (`STAbc.VALUE`); their Java names are `STAbc` too.

### 6.2 The object factory

docx4j's `ObjectFactory` (10,821 lines) is 375 no-argument creators and 834 `JAXBElement`
wrappers. docx4j-core-ts CR-002 section 3.2 found the creators nearly redundant in TypeScript
and the wrappers essential, and generated both. The Python situation is different again:

- **Creators are redundant.** Every generated class is a keyword-only dataclass with all fields
  optional (section 3), so `P(p_pr=PPr(...), content=[R(...)])` is the creator and the compiler's
  shape check is the runtime's `TypeError` on an unknown keyword.
- **Wrappers are unnecessary but their knowledge is not.** xsdata bakes element identity into the
  class: a `w:t` in a run is one class, a `w:delText` another, `w:ins` and `w:del` around runs
  are subclasses of the shared type with their own `Meta.name`. There is no `JAXBElement`. But the
  user then has to know that a run's text is `wml.Text` and not `dml.Text`, and which class an
  element name takes in which scope, which is exactly what `ObjectFactory` knew.

Decision: generate, from the class metadata rather than from the schema, a per-namespace `el`
module and a hand-written sugar layer on it, as CR-002 section 3.2 did:

```python
from docx4j_py.wml import el, p, r, t, tbl, wml, text_of, walk, find

el.p(content=[el.r(content=[el.t("Hello World")])])   # el.<element name>(...) -> the right class for that element in that namespace
el.t("  two spaces  ")                                # sets xml:space="preserve"
p("Hello", style="Heading1")                          # the text-in sugar: run and text made for you
r("bold", bold=True)
para = wml('<w:p><w:pPr><w:pStyle w:val="Heading1"/></w:pPr><w:r><w:t>Hello</w:t></w:r></w:p>')
                                                      # the standard declarations added (docx4j W_NAMESPACE_DECLARATION), parents linked
text_of(para)                                         # docx4j TextUtils
walk(root, visitor); find(root, P)                    # TraversalUtil, ClassFinder
```

- `el` is generated once per namespace by a script in `codegen/` that walks the `XmlContext`
  metadata of every class: for each element name in the namespace, the class it maps to; where
  one name maps to several types by scope (`w:t` in `w:r` and in `m:r`; `w:sdt` block, run, row
  and cell), the function takes the intended class from its arguments or is offered per scope
  (`el.r_t`, `el.sdt_block`), and the table of these is committed and reviewed. Everything `el`
  builds has its parent linked when placed by `ChildList`.
- The sugar (`p`, `r`, `t`, `tbl`) is hand-written and small; it is the text-in convenience, not a
  second factory.
- `wml(...)` parses a fragment with the prefix table of section 7 declared on a synthetic wrapper,
  returns the typed object with parents linked, and accepts several siblings (`wml.all`).
  `to_xml(obj)` is the inverse, for a fragment; part-level serialisation is the engine's.
- `text_of`, `walk`, `find` are generic over the metadata (no per-class code) and are what the
  content API and agents use to address content before CR-003 lands.

## 7. Schemas, prefixes, parsing and serialising

- **The schema copy** under `schemas/` is docx4j's `xsd/` tree with marked patches, each a
  comment beginning `docx4j-python:`. *(CR-002 Phase A, 2026-09-12: it also holds
  `relationships.xsd` and `docProps/` now, for the `.rels` and document-properties parts the
  engine needs — CR-002 section 9 — and gained two more patches, `CT_StylePaneFilter` and the
  `w14:docId` order; `schemas/PATCHES.md` 3 and 4.)*: `w:dir` and `w:bdo` anonymous types promoted (done);
  `xsd:anyAttribute processContents="lax"` on every part-root complexType (`CT_Document`,
  `CT_Styles`, `CT_Fonts`, `CT_Numbering`, `CT_HdrFtr`, `CT_Settings`, `CT_Footnotes`,
  `CT_Endnotes`, `CT_Comments`, ...) so `mc:Ignorable` and future `w16*` root attributes
  survive. Stripping `default="..."` is *not* a schema patch: the fork flag keeps the default in
  metadata so a resolver can ask for it.
- **The prefix table** is docx4j's `NamespacePrefixMapper` as a Python dict (`w`, `r`, `wp`, `a`,
  `pic`, `v`, `o`, `w10`, `w14`, `w15`, `w16se`, `w16cid`, `w16`, `mc`, `m`, `wps`, `wpg`, `c`,
  `dgm`, `xml`, ...) in `docx4j_py.namespaces`, used by `wml(...)` and by the engine. The
  serialiser is always called with an explicit `ns_map`; the reconciliation of the root's
  declarations with `mc:Ignorable` is the engine's (CR-002), as in docx4j-core-ts.
- **Strict by default in tests, lenient in production, never silent.** `ParserConfig` with
  unknown properties and attributes allowed, and the fork's skipped-content report attached to
  the parse result; the engine logs it per part at warning level and exposes it on the part.
  The round-trip harness fails on any skipped node.
- **Until the fork lands,** `scripts/roundtrip.py --tolerant-factory` shows the `class_factory`
  that fills missing required fields with `None`; the object model ships that factory as a
  stop-gap so the engine can be started against the current generated code.
- **MCE preprocessing** (`mc:AlternateContent` resolved before unmarshalling) is the engine's
  concern and is not needed for fidelity: both branches round-trip as typed `mce` objects today.
  *(CR-002 Phase A, 2026-09-12: confirmed. The engine does not preprocess by default; the
  resolution is a view, `mce="resolve"` on `iter_children` and the traversal functions, with
  `docx4j_py.namespaces.UNDERSTOOD` generated from the model. `LoadOptions(mce_preprocess=True)`
  is the opt-in that does what docx4j does. CR-002 section 12.6.)*
  docx4j-core-ts found it *required* because its model typed `mc:AlternateContent` only where a
  global element could follow; xsdata's compound fields include it wherever the schema allows
  it, and `w:drawing` inside `mc:Choice` parsed in the `DrawingML_GraphicData_wps.docx` and
  `2010-glow-then-AlternateContent.docx` fixtures. To be re-checked once the layout changes.

## 8. Process model and performance

Measured 2026-09-12 with the unmodified generator (REPORT.md sections 4 and 5):

| | value |
|---|---|
| import, warm / cold | 0.86 s / 1.33 s |
| modules imported / resident memory | 1,755 / 46 MiB |
| parse throughput | 3.0 MiB/s (lxml handler) |
| serialise throughput | 2.0 MiB/s |
| bare lxml, for comparison | 69.5 MiB/s |
| 772 KiB `document.xml`, parse + serialise | 0.26 s + 0.38 s |

Accepted (2026-09-12) on the condition that the library runs in a **long-lived process** that
imports once and handles many documents: a server, an MCP server, a daemon behind a CLI. One
process per document is not a supported deployment for large volumes. Consequences:

- `XmlContext` builds class metadata lazily on first use, so the first document after start-up
  pays extra. The package offers `warm_up()`, which parses an embedded representative document.
- Thread safety of a shared `XmlContext` and parser across concurrent documents is **to be
  verified** before any concurrent server is built; until then one context per worker.
- The parent-linking walk and `ChildList` add to the parse figure above; the budget is 20%.
- Serialisation slower than parsing is noted; work on it waits for a document that is too slow.

## 11. Open questions (decided 2026-09-12)

All six recommendations below were accepted on 2026-09-12 and are now decisions.

1. **docx4j's names or the schema's.** Recommendation: docx4j's (`P`, `PPr`, `CTSettings`), for
   continuity with fifteen years of docx4j examples and with docx4j-ts; the schema names
   (`CT_PPr`) as aliases are cheap if wanted later.
2. **Element-specific subclasses versus one class with a name.** xsdata generates `RunIns` as a
   subclass carrying `Meta.name`; JAXB used one class and a `JAXBElement` name. Recommendation:
   keep xsdata's subclasses; `isinstance(x, CTRunTrackChange)` still works and there is nothing
   to unwrap. Check the effect on `find(root, CTRunTrackChange)` (it must match subclasses).
3. **Parser hook versus post-parse walk for parents.** Recommendation: the walk in Phase B, the
   hook only if the walk exceeds its budget.
4. **`--slots`.** Recommendation: keep it; the `parent` slot on `Child` removes the objection,
   and memory matters for 100k-paragraph documents.
5. **Boolean spelling on output** (`true` against Word's `1`). Recommendation: write `1`/`0` as
   Word does, through a converter registered on the fork's runtime, so saved documents diff
   cleanly against Word's own.
6. **Whether `el` functions accept positional text** (`el.t("x")`) or only keywords.
   Recommendation: positional for the text-carrying element classes only (`Text`, `DelText`,
   `w:instrText`), keywords everywhere else.
7. **(added 2026-09-16, undecided) One repository or two.** docx4j-core-ts keeps the generated
   objects and the engine in separate repositories (and jsonix in a third); here the model, the
   engine (CR-002) and the content API (CR-003) share one repository and one distribution, which
   was assumed rather than decided. The TypeScript reasons that do not carry over: add-in bundle
   size (no Python equivalent) and a separate runtime (the xsdata fork already is one). The one
   that does: regeneration churn in the history, which Phase D will roughly triple. Against a
   split: the TypeScript CR-002 notes record seven tree-layer builders written in core-ts and
   later moved to the objects package with releases on both sides; that seam (`child.py`,
   `traversal.py`, `fragments.py`, the builders, CR-003 Phase A) is where work lands first and
   settles later, and in one repository the move is a rename. Recommendation: one repository;
   revisit at Phase D and, if churn or wheel size warrants it, split into two *distributions*
   (`docx4j-objects`, `docx4j-py`) within it rather than two repositories.

## 12. Phase A implementation notes (2026-09-12)

The fork is `~/git/docx4j-xsdata`, branch `docx4j`, on upstream tag v26.2 (`7a82d771`), local
only, nothing pushed. Its `docs/fork/CHANGES.md` is the authoritative list of differences and
`docs/fork/REBASING.md` the procedure. Seven commits: fork tooling; the script-generated rename
(`tools/rename.py`, 322 files, regenerated by `tools/rebase-upstream.sh` for each upstream tag,
verified against v26.2 both ways); then one commit per generator option, each with tests under
`tests/fork/`, each defaulting to upstream behaviour; then the docs. Test suite: 1,122 passed and
17 skipped against upstream's 1,103 and 17. No new CLI flags; all four options are `<Output>`
children of `.xsdata.xml`:

```xml
<AllOptional>true</AllOptional>                        <!-- default false: every element and attribute field None | T = None -->
<SchemaDefaults>metadata</SchemaDefaults>              <!-- default field: schema default kept as metadata "schema_default", XmlVar.schema_default at runtime; parser never fills it -->
<ListFactory>docx4j_py.child.ChildList</ListFactory>   <!-- default unset: default_factory for every list field, imported into each module -->
<DeferredImports>true</DeferredImports>                <!-- default false: the namespaces layout imports -->
```

Departures from the text above, all deliberate:

- **Circular imports (section 3, 6.1).** Not `TYPE_CHECKING` imports. Postponed annotations
  already make type hints strings, so a module keeps at the top only what class creation needs
  (base classes, `default=` values, enum members); everything else is imported below the classes
  and compound-field `choices` reference classes as `ForwardRef("Name")`, which the runtime
  already resolves. Two consequences: package `__init__` re-exports go through a module
  `__getattr__` (an eager re-exporting `__init__` makes the package atomic and defeats any
  ordering), and the root package carries an import-order manifest, the strongly connected
  components of the module graph in dependency order. Module-alias qualification was rejected for
  readability; a per-module lazy `__getattr__` cannot work because `typing.get_type_hints`
  resolves against the module's real `__dict__`.
- **Two more upstream bugs** surfaced under the namespaces layout and are in `docs/UPSTREAM.md`:
  a namespace URI that prefixes another yields a module shadowed by a same-named package (worked
  around with a module-name substitution; Phase B must carry it in `.xsdata.xml`), and
  cross-module circular references were never imported (fixed in the fork).
- **Round trip on the namespaces layout,** WML in 103 modules, all importable: with the earlier
  tuned settings, exactly REPORT.md config B (18 of 50 parts identical; zero element, order or
  text differences). With `AllOptional` and `SchemaDefaults=metadata` and no tolerant class
  factory and no ignore-defaults: 19 of 50 identical, `attribute-added` 0 (was 5,516),
  `attribute-dropped` 10 (was 773; all `mc:Ignorable` on `w:fonts`, the `anyAttribute` schema
  patch of section 7 is Phase B), `attribute-value` 3,034 (all the `1`/`true` spelling, open
  question 5, Phase B). `invoice2013.docx` parses unaided. Section 3's first two rows are
  therefore closed.
- **Names under the namespaces layout:** suffixed duplicate class names fall from 213 to 10 and
  `CtText3` is gone (`CtText` is per namespace); `w:t` in a run is still the nested `R.T`. The
  docx4j name table and unnesting remain Phase B.
- `scripts/roundtrip.py` gained `--package`, `--models-module` and `--runtime` so it can be
  pointed at any generated package and at either runtime. The project's `.venv-fork` has the fork
  installed editable; `.venv` and the unmodified-xsdata baseline are kept for comparison, the
  baseline having moved to `baseline/docx4j_py/generated/` at the Phase B integration stage
  (section 13.8).

### 13.3 Names: what the table could and could not buy

The fork's `<ClassNames>` option reads `codegen/names/`. Applied naively it made the output
**worse** — 333 numerically suffixed class names against 82 with no table at all, with `Text1`
for `CT_Text` and `Text2`..`Text7` spread over the elements that share it. The reason is
structural and is the same one section 6.2 already knew about the object factory: **JAXB has one
class where xsdata has several.** docx4j's `ObjectFactory` maps 27 element names onto
`BooleanDefaultTrue` and three onto `Text` because those are `JAXBElement` wrappers over a shared
payload class, and the table's `types` section already names that class. xsdata instead invents an
intermediate class per element name wherever a compound field has two elements of one type, and
those classes have no xml name of their own at all — the element name lives in the `choices`
metadata of the field.

**The decision** (implemented in the fork, commit `930ccd57`, with its own tests):

1. An intermediate choice class is renamed **only by a scoped entry**. The generator records the
   enclosing class on it (`Class.scope_name`, the analogue of JAXB's `@XmlElementDecl(scope=...)`)
   and the table's `elements` keys may carry a scope, `t@CT_R`, read in the namespace of the file
   that holds it. An unscoped entry never reaches one.
2. An element entry **never takes a name another class owns**. `types` is applied first, so the
   class the schema declares as a type keeps the bare name and the element entry is dropped with a
   warning rather than applied and then suffixed.

Result: **79 suffixed names out of 1,995 classes**, against 82 with no name table at all (and 85
before `codegen/names/wml_overrides.json` named the run's three text classes) — the table now
costs nothing. Two of the 79 are false positives of the counting, `CT_Integer2` and
`CT_Integer255` of OMML being schema names rather than suffixes, which leaves **72 intermediate
choice classes and 5 type classes behind a same-named global element**. Every name section 6.1 promised is there and bare: `P`, `R`, `Text`, `PPr`, `RPr`,
`Body`, `Document`, `Tbl`, `Tr`, `Tc`, `Style`, `Styles`, `CTSettings`, `CTShd`, `RunIns`,
`RunDel`, `BooleanDefaultTrue`, `CTMarkup`, `CTTrackChange`, `SdtBlock`, `JcEnumeration`, and the
part roots. `tests/test_names.py` pins them, and pins that `Meta.name` is still the *schema's*
name, so a rename never changed the document a class reads or writes.

What is left, and why it is acceptable:

- **72 intermediate choice classes** keep generator names: `T1`/`T2` for `w:t`, `Ins1`/`Ins2`,
  `Del1`/`Del2`, `InstrText1`/`InstrText2`, `MoveTo1`/`MoveTo2`, the `CustomXml*Range*` pairs, the
  `EndnoteReference`/`FootnoteReference` pairs, and the DrawingML colour percentages
  (`Red1`/`Red2` and friends). docx4j has **no** class for any of them, so there is no name to
  take; each is a subclass of the type the table did name, so `isinstance(x, Text)` and
  `find(root, CTRunTrackChange)` work exactly as open question 2 promised. The three a user
  touches daily are named by the one hand-written scoped entry in the tree,
  `codegen/names/wml_overrides.json`: `w:t`, `w:instrText` and `w:delInstrText` inside `w:r` are
  **`RT`**, `RInstrText` and `RDelInstrText`, the same shape the generator already gives their
  siblings (`R.Cr` is `RCr`, `R.Tab` is `RTab`) and the same shape docx4j gives them in Java.
- **Five type classes take a `1`**: `Body1`, `Graphic1`, `Pic1`, `Anchor1`, `Inline1`. In each
  case a global element of the same name exists, xsdata generates a class for each, and the
  element class — which is the one the containing field actually refers to, `Document.body` is a
  `Body` — keeps the bare name. The `1` is on the base class.
- **MathML's 34 `OperatorType` elements and DrawingML's 15 `CTPercentage` elements** keep
  generator names for the same reason as the intermediate classes; the shared type has the docx4j
  name.
- **`m:rPr` and `m:t`** still have no entry: docx4j resolves them to the inner Java classes
  `CTR.RPrMath` and `CTMathRunTrackChange.TMath`, which are not expressible as Python class names.
  The other four of the six scope collisions section 13.5 (below) reported are resolved:
  `codegen/derive_names.py` now drops candidate classes that the `types` section already names,
  which resolves `w:sdt` to `SdtBlock` outright and shows `w:sdtContent`, `w:customXml` and
  `cx:lvl` to have needed no entry at all — every candidate was already named by its type.

### 13.5 Departures from sections 5, 6 and 7

1. **Section 6.1's package list cannot be taken literally.** `docx4j_py.dml` and
   `docx4j_py.dml.wordprocessing_drawing` cannot both exist: in Java a package holds classes and
   subpackages, in Python a name is a module *or* a package. DML main is generated as
   `docx4j_py.dml.main` and reached as `docx4j_py.dml.Graphic` through the package's lazy
   `__init__`. `docx4j_py.wml`, `docx4j_py.math`, `docx4j_py.mce`, `docx4j_py.w14`,

2. **`docx4j_py.vml`, `docx4j_py.w16*` and `docx4j_py.relationships` are not in this output.**
   VML and the 2016 namespaces are not in `schemas/wml/wml.xsd`'s import closure at all — `w:pict`
   reaches VML through an `xsd:any` — and the relationships schema in the closure declares only
   global attributes, so it yields no classes. All three are Phase D, not Phase B.
3. **`docx4j_py/__init__.py` is generated.** The import-order manifest `DeferredImports` needs
   lives there, so importing `docx4j_py.child` imports the whole model. Section 8's import figure
   is therefore the cost of touching *anything* in the package until Phase D makes it lazy.
4. **`ST_Jc` does not exist.** Section 6.1 cites `STAbc` enum names; docx4j's own `wml.xsd`
   renames `ST_Jc` to `JcEnumeration`, and the name tables are keyed on docx4j's schema, not stock
   ECMA-376. `codegen/names/README.md` lists all 62 such inline `jaxb:class` renames.
5. **Six element names had no entry in the name tables** because JAXB resolved them by scope and
   the table format had no scope: `w:sdt`, `w:sdtContent`, `w:customXml`, `m:rPr`, `m:t` and
   `cx:lvl`. Four are resolved and two are not; see 13.3.
6. **The walk is depth-first, not post-order** (section 5). Assigning a parent pointer is
   order-independent, and a single pre-order pass is the cheaper of the two.
7. **7.2b got worse before it gets better.** Now that `mc:Ignorable` survives on every part root,
   six parts rather than four declare prefixes the fixed `ns_map` does not (`w16se`, `w16cid`).
   The reconciliation is still the engine's (CR-002), and it is now unambiguously required.
8. **Section 9's "other than boolean spelling" is now a category, not a caveat.**
   `scripts/canon.py` has `boolean-spelling`, reported separately and excluded from the identical
   verdict; every other category must be zero or the harness fails.

### 14.1 `el`, and where it lives

`codegen/generate_el.py` (734 lines) walks the `XmlContext` metadata of all 1,673 generated
classes — the element vars of each class, the `choices` of each compound field, and each class
that is itself a global element declaration — and emits one `el` module per namespace. Nothing
reads the schema.

| | Phase C |
|---|---|
| `el` modules / lines / size | 53, 20,488 lines, 1.1 MB |
| element names, all namespaces | **1,964** over 51 namespaces (two namespaces have none) |
| scope-qualified names | **225** |
| keyword or builtin renames | **29** |
| element names with more than one class | **153** |
| element names with no class at all | **56** (a simple type; listed, not built) |

| committed tables | `codegen/el_tables/*.json`, 53 files, 352 KB |

**The layout departs from the deliverable's literal path, and from section 13.5 point 1 in the
same direction.** `el` has to be `docx4j_py.wml.el`, but the generator emits `docx4j_py/wml.py`,
a module. `generate_el.py` therefore turns every namespace *module* into a *package of the same
name* (`docx4j_py/wml/__init__.py`) before writing `docx4j_py/wml/el.py`. The module **name**
never changes, so the generated cross-module imports, the import-order manifest in
`docx4j_py/__init__.py` and the lazy `__getattr__` of the package inits all keep working
untouched; `codegen/generate.sh --check` proves the whole tree is still byte identical over two
runs, now 118 modules. The one wrinkle is that `docx4j_py/wml/` holds a hand-written
`builders.py` next to two generated files: `codegen/clean.py` keeps a path list rather than a
name list, and leaves the directory in place with no `__init__.py`, which makes it a
namespace-package portion that loses the import to the freshly generated `docx4j_py/wml.py` —
so xsdata's own import check still sees the module, and `generate_el.py` then merges the two.

Each namespace package also gets a generated footer: a PEP 562 module `__getattr__` that
resolves `el`, `wml`, `to_xml`, `text_of`, `walk`, `find`, `warm_up`, `link_parents`,
`deep_copy` and (for WML) the sugar, lazily — eagerly would be an import cycle, since every one
of them imports the classes the module defines.

### 14.2 The naming rules

**Primary name: the element's local name, verbatim.** `el.p`, `el.pPr`, `el.tblGrid`,
`el.customXml` — what the user types is what the document holds, which is the rule
`docx4j-generated-objects-ts`'s `el/*` follows too. Two adjustments: a character an identifier
cannot hold becomes `_`, and a name that is a Python **keyword, soft keyword or builtin** takes
a trailing underscore. In WML that is exactly seven: `del_`, `dir_`, `format_`, `id_`, `next_`,
`object_`, `type_` (29 over all namespaces). `el.name` needs none — `name` is neither a keyword
nor a builtin — and the rule is mechanical rather than a list, so a future schema cannot sneak
a `class` or a `lambda` past it.

**Which class a bare name builds**, in order of precedence, recorded per entry in the table as
`chosen_by`:

1. an `overrides.defaults` entry a human wrote in `codegen/el_tables/<ns>.json`;
2. the class that **is** the global element declaration for that name — `SdtBlock` for `w:sdt`,
   `RunIns` for `w:ins`, `RunDel` for `w:del`, `Document` for `w:document` — which is docx4j's
   own answer, since those names come from the schema's `jaxb:class` customisations;
3. the class whose declaring scopes are the most **reachable**: each scope class is weighted by
   how many scopes declare it in turn. A plain count of scopes got this wrong for a whole family
   of names — `w:tab`, `w:cr`, `w:sym`, `w:ptab`, `w:noBreakHyphen` and the rest are declared in
   one scope by `R` (which 42 classes hold) and in three by the OMML run's track-change classes
   (which two do), so counting scopes made `el.tab()` a *maths* tab. Weighting fixes all of them
   at once and needs no override;
4. the most scopes, then the alphabetically first class name, so the output never depends on
   dictionary order.

Four WML overrides were needed after that, and they are the whole hand-written input:
`hyperlink` → `PHyperlink` (seven classes, one per container, all equally reachable; docx4j's
`P.Hyperlink` is the one people mean), `name` → `StyleName` (seven, all reachable once),
`spacing` → `CtPprBaseSpacing` (paragraph spacing over character spacing, a judgement),
`customXml` → `CTCustomXmlBlock` (for symmetry with `el.sdt`, which rule 2 makes block-level).

**The scope-qualified name of every other class** of a colliding element name is
`snake(class name)` with a leading `ct_` dropped, and, when that tag is not unique in the
namespace, the element name in front of it. It reads well because the generated class names
already say which container they belong to:

```
el.sdt          SdtBlock            el.customXml         CTCustomXmlBlock
el.sdt_run      SdtRun              el.custom_xml_run    CTCustomXmlRun
el.sdt_row      CTSdtRow            el.custom_xml_row    CTCustomXmlRow
el.sdt_cell     CTSdtCell           el.custom_xml_cell   CTCustomXmlCell
el.hyperlink    PHyperlink          el.left              CTBorder
el.bdo_hyperlink       CtBdoHyperlink              el.left_tbl_width     TblWidth
el.simple_field_hyperlink  CtSimpleFieldHyperlink   el.right_tbl_width    TblWidth
```

`left_tbl_width` is the second form: `TblWidth` serves eight element names (`w:left`, `w:right`,
`w:top`, `w:bottom`, `w:start`, `w:end`, `w:tblCellSpacing`, `w:tcW`), so its tag is not unique
and every one of them is qualified. Five alias overrides give the names a mechanical rule cannot
know: `el.t_math` (`w:t` inside OMML's `CTR`, docx4j's `CTR.TMath`), `el.ins_math`,
`el.ins_ctrl_pr`, `el.del_math`, `el.del_ctrl_pr`.

**The 72 intermediate choice classes of section 13.3 are exactly what `el` was for.** They have
no element name of their own — `RT` is `w:t` only because `R.content` says so — so `el.t(...)`
is the only sane constructor for them, and `to_xml` needs the same table to know what to call
the root. `el.CLASS_TO_QNAME` is that table, emitted per namespace for the 454 WML classes that
stand for exactly one element name.

**Positional text** (decided question 6) is generated for a class whose metadata has a text value
field, and for no other: `el.t("x")`, `el.delText("x")`, `el.instrText(" PAGE ")`, and
`el.p("x")` is a `TypeError`. `xml:space="preserve"` is set when the text begins or ends with
whitespace or holds two whitespace characters in a row, which is docx4j's `t()` and
`builders/wml.mts`'s `t()` to the character.

### 14.3 The sugar

`docx4j_py/wml/builders.py`, hand written, 400 lines, re-exported from `docx4j_py.wml`:
`p(*runs_or_text, style=None, run_style=None, **ppr)`, `r(*text_or_children, **options)`,
`t(text)`, `tbl(rows, style=None, widths=None, width=9026)`, `br(type=None)`, `tab()`, and the
run-option pair `apply_run_options` / `read_run_options`.

The run options are `builders/wml.mts`'s, in the same vocabulary (Office JS `Word.Font`, so that
what a builder sets a view reads back under the same name) spelled `snake_case`: `bold`,
`italic`, `underline`, `strike_through`, `double_strike_through`, `subscript`, `superscript`,
`name`, `size`, `color`, `highlight_color`, `style`. `None` leaves a property alone; `False`,
`''`, `'None'` and `null` remove it. The seventeen-entry underline table and the sixteen-entry
highlight colour table are ported from the TypeScript (`UNDERLINE`, `HIGHLIGHT_COLORS`, and
docx4j's `Highlight.getHexVal` / `setVal` as `highlight_hex_value` /
`highlight_name_for_color`). Departures, both deliberate:

- **`font` is accepted as an alias of `name`.** `r(text, name='Calibri')` is right by parity and
  confusing as a Python keyword argument; both work and `tests/test_builders.py` pins that they
  produce the same `w:rPr`.
- **`p` and `r` are variadic**, `p('a', r('b'), 'c')`, where the TypeScript has two overloads
  (a string or a list). `p` also forwards any other keyword to `w:pPr`
  (`p('x', keep_next=el.keepNext())`), so the sugar never becomes a wall a user has to climb
  over to reach a property it does not name.

### 14.4 Fragments

`docx4j_py/fragments.py`: `wml(xml, *, wrapper=None, lenient=False)`, `wml.all(...)`,
`to_xml(obj, *, pretty=False, name=None)`. The fragment is wrapped in a synthetic
`<w:fragment>` carrying **every** prefix of `docx4j_py.namespaces` (docx4j's
`NamespacePrefixMappings.getPreferredPrefixStatic`, extracted mechanically on 2026-09-12: 125
mappings, plus SpreadsheetML main, which the Java returns conditionally, and three namespaces
docx4j has no entry for at all but this repository generates classes for — MathML, InkML and
`sharedTypes`, given the conventional `mml`, `inkml` and `st`; `tests/test_runtime.py` fails if
a generated namespace ever has no prefix). Declarations inside the fragment win.

**Three departures from `builders/wml.mts`**, all because the Python runtime is less constrained
than the TypeScript one:

1. **No wrapper chain.** The TypeScript runtime can only unmarshal a *global* element, so it has
   to wrap a `w:tbl` in a `w:body` and dig the result out again. `XmlParser.from_bytes(data,
   clazz)` is told which class to build and does not check the root element's name, so every
   fragment is parsed **directly** as the class the `el` table gives for its qualified name.
   `wml('<w:pPr/>')` is a `PPr`; the TypeScript cannot do that at all.
2. **`wrapper=` is a scope, not a container to build.** Where one element name is several classes,
   `wml(xml, wrapper='p')` resolves it the way a paragraph would (`SdtRun`), `wrapper='tbl'` the
   way a table would (`CTSdtRow`), and a class is accepted as well as a name. It is looked up in
   the wrapper class's own metadata, so it needs no table of its own. The TypeScript infers the
   wrapper from the first decisive descendant; here the caller says, because the caller in
   CR-002/CR-003 always knows where it is about to put the fragment. Inference could be added
   later without changing the signature.
3. **Strict by default.** A fragment that loses anything raises `FragmentError` naming what was
   lost, from the fork's skipped-content report; `lenient=True` accepts the loss. That is
   section 7's "never silent" at the fragment level, and it is load-bearing: parsing a run-level
   `w:sdt` as the block-level class silently drops the run, and now says so.

`to_xml` serialises with the whole prefix table (so the serialiser never invents `ns0`), renames
the root when the class has no element name of its own (the 72 intermediate classes), then trims
the declarations the fragment does not use with `lxml.etree.cleanup_namespaces`, **keeping every
prefix an `mc:Ignorable` in the fragment names** — which is the reconciliation of section 13.5
point 7, done for fragments; the part-level one is still CR-002's. Booleans are numeric. A class
that stands for several element names (`TblWidth`) has no name of its own and `to_xml` raises
rather than guessing; `name=` settles it.

Round trip: `to_xml(wml(x))` is canonically equal to `x` — `scripts/canon.py`'s normal form, the
same verdict the corpus uses — for **fourteen** fragments including `w14:paraId`/`w14:textId`,
`xml:space`, `r:id`, `mc:AlternateContent` with a `wps` `mc:Choice` and a `mc:Fallback`, OMML,
a content control, a tracked insertion, a table with a grid, and a bare `w:pPr`.

### 14.5 Traversal

`docx4j_py/traversal.py`: `walk(root, visitor)`, `iter_nodes(root)`, `find(root, cls_or_tuple)`,
`text_of(obj)`, `element_name(obj)`. All metadata-driven, and the child enumeration is **shared
with `link_parents`**: `docx4j_py.child.iter_children` yields `(element qualified name, child)`
from a per-class plan built once from the metadata, and `link_parents`, `iter_tree`, `walk`,
`iter_nodes` and `text_of` are all built on it. Refactoring `link_parents` onto the shared plan
made it **faster**: `scripts/parents.py` now reports **7.2--7.3%** of parse against 9.4% at the
end of Phase B, still 0 parent problems over 34,147 nodes.

- `walk`'s visitor is `(node, parent, element name)` and returns `False` to stop descending, as
  docx4j's `TraversalUtil` callback does; `iter_nodes` is the generator form.
- `find` uses `isinstance`, so decided question 2's check passes: `find(root, CTTrackChange)`
  returns the `RunIns` and `RunDel` nodes and `find(root, Text)` the `RT` ones. **One asymmetry
  found:** `DelText` is *not* a subclass of `Text` — xsdata generated the global element
  `w:delText` as its own class rather than as a subclass of `CT_Text`, unlike `RT` — so
  `find(root, (Text, DelText))` is how to ask for both. Noted, not fixed; it is a generator
  shape, not a defect.
- `element_name` is what makes `text_of` possible: 72 classes have no name of their own, so the
  name comes from the parent's metadata, and at the root from `el.CLASS_TO_QNAME` or, failing
  that, from the class's own `Meta` when it declares a `namespace` as well as a `name` (which is
  exactly what xsdata emits for a global element and never for a type). **`XmlMeta.qname` must
  not be used for this**: xsdata builds a *type* class's qname against whatever parent namespace
  it first met the class in and caches it, so `PPr` reads `CT_PPr` before any parse and
  `{...}CT_PPr` after one. That cost an afternoon and is now pinned by a test.
- `text_of` is docx4j's `TextUtils` and `builders/wml.mts`'s `textOf`, keyed on element names
  rather than classes, so it needs no per-class code and handles `RT`, `Text` and every other
  `w:t` class at once: `w:t`, `w:tab` (`\t`), `w:br` and `w:cr` (`\n`), `w:noBreakHyphen`
  (U+2011), `w:softHyphen` (U+00AD), `w:sym` (its `w:char`); runs inside `w:hyperlink`, `w:sdt`,
  `w:sdtContent`, `w:smartTag`, `w:customXml`, `w:ins`, `w:moveTo`, `w:dir`, `w:bdo` and
  `w:fldSimple` are read; `w:del` and its `w:delText` are skipped and so are `w:instrText` and
  `w:delInstrText`; paragraphs are joined with a newline.

**Parity result: exact.** `tests/test_traversal.py` compares `text_of` against an independent
lxml extraction that follows the same rules, over the `document.xml` of all **13** documents in
`samples/`: identical on every one.

### 14.6 `warm_up()` and the numbers

`docx4j_py/runtime.py` holds the shared `XmlContext`, the parser and serialiser factories and
`warm_up()`, which parses two hand-written parts under `docx4j_py/resources/` — a
`document.xml` with paragraph and run properties, a style reference, a hyperlink, a field, a
bookmark, a content control, a tracked insertion and deletion, a table with a grid and borders,
two drawings, an `mc:AlternateContent`, OMML, `w14` attributes, a symbol, a break and a tab, and
a `styles.xml` with `docDefaults`, latent styles and paragraph, character, table and numbering
styles. Both parse with **nothing skipped**, which a test keeps true.

Measured 2026-09-12, `tables.docx`'s 24 KB `document.xml`, a fresh process each time, three runs:

| | cold | after `warm_up()` |
|---|---:|---:|
| `import docx4j_py.wml` | 651–675 ms | 657–658 ms |
| `warm_up()` | — | 43–47 ms |
| class metadata built before the first parse | **0** | **114** |
| first parse | **54–57 ms** | **37–41 ms** |
| classes the first parse still has to build | 15 | 1 |
| steady-state parse (5 more) | 24–27 ms | 23–24 ms |

So `warm_up()` removes about two thirds of the first-document penalty and leaves 1 class to
build instead of 15. It does not pay for itself on a *single* document — it costs 45 ms to save
17 — and it is not meant to: it moves the cost to start-up, which is the whole point of section
8's long-lived process. The other samples need 1, 4, 6 and 23 more classes after a warm-up, so
the 114 are the common ones. `warm_up()` is idempotent and returns the seconds it spent.

### 14.7 Thread safety: the verdict

`scripts/threads.py` parses and serialises **71 parts from 13 documents**, five times over, on
**8 threads**, in three configurations, and compares every byte and every skipped-content report
against a sequential run. What the fork's code says, and what the run shows:

| configuration | jobs | output differences | report differences | failures |
|---|---:|---:|---:|---:|
| one `XmlContext` per thread | 355 | 0 | 0 | 0 |
| **one shared `XmlContext`**, a parser per parse | 355 | **0** | **0** | **0** |
| one shared `XmlContext` **and one shared parser** | 355 | 0 | **0 or 1**, it is a race | 0 |

**Verdict: a shared `XmlContext` is safe; a shared `ParserConfig` is not.**

- `XmlContext` holds two caches that only ever grow (`cache`, class → `XmlMeta`, and
  `xsi_cache`), and `build()` is `if clazz not in cache: cache[clazz] = builder.build(...)`.
  Two threads racing on the same class each build the metadata and the last assignment wins; the
  metadata is a function of the class, so they agree and the race only wastes work. Nothing
  invalidates the cache. Sharing it is what makes `warm_up()` worth anything across workers.
- `NodeParser` keeps **no** per-parse state on itself — the `queue` and `objects` lists live on
  the handler, which `parse()` constructs per call — with one exception: **`ParserConfig.skipped`**,
  the fork's skipped-content report, is a list on the config that the parser clears at the start
  of every parse and appends to during it. Two threads through one config therefore read each
  other's report. Forced into the open (`scripts/threads.py` races the one part of the corpus
  that actually loses content, `toc.docx`'s `settings.xml`, against one that does not): **7 to 19
  of 500** reads of `parser.skipped` were another thread's, over several runs. The parsed documents were byte-identical
  throughout — it is the report that is wrong, not the tree, which is worse in its way, because
  a caller that fails on the report would fail on the wrong part.
- `XmlSerializer.render` builds its writer per call and holds nothing.

So **the CR's rule is: one `ParserConfig` (and therefore one `XmlParser`) per thread, one
`XmlContext` per process.** `docx4j_py.runtime.parser()` returns a new parser with a new config
every call and says so in its docstring; `context()` is a double-checked singleton.
`tests/test_threads.py` is the short version of the script and runs in the suite.

### 14.8 Departures from section 6.2, and one defect found

1. **The layout** (14.1): namespace modules become packages; `el` is `docx4j_py.wml.el`, not a
   sibling module.
2. **`wrapper=` is a scope rather than an inferred container** (14.4 point 2), and fragments are
   parsed directly rather than through a wrapper chain.
3. **`el` does not cover 56 element names, in 51 namespaces, because they have no class**: their
   schema type is a simple type, so xsdata put the value on the parent directly. In WML there is
   exactly one, `w:uniqueTag` (`xsd:base64Binary`, inside `w:recipientData`). They are listed in
   each table under `simple_type_elements` rather than quietly absent, and the coverage test
   asserts the list rather than ignoring it.
4. **One class has no metadata at all and is therefore not in `el`:** `docx4j_py.inkml.MappingType`
   raises `NameError: name 'Math' is not defined` when its metadata is built. The generated
   `inkml` module has a `ForwardRef("Math")` in the choices of `mapping` and never imports
   MathML's `Math` — the fork's `DeferredImports` collector misses a cross-module reference that
   appears only inside compound-field choices. It costs the element `{InkML}mapping` its `el`
   entry and would make an inkml `mapping` holding MathML unparseable. **Not fixed in Phase C**
   (it is a generator bug, and fixing it means a fork commit and a regeneration); recorded here
   and in `docs/UPSTREAM.md` for Phase D.
5. **A second fidelity gap the Phase C work surfaced**, outside the 50 parts `scripts/roundtrip.py`
   covers: `w:stylePaneFormatFilter` in `settings.xml` is typed `CT_ShortHexNumber` in docx4j's
   schema copy, but Word writes the ECMA-376 2nd-edition `CT_StylePaneFilter` attributes on it,
   so **15 attributes are dropped** from `toc.docx`'s `settings.xml`. The skipped-content report
   catches it, which is the report doing its job. The fix is a schema patch (section 7) and
   belongs with CR-002, which is the first thing that will actually save a `settings.xml`.
6. **`DelText` is not a `Text`** (14.5).
7. **`el.settings()` is `Settings`, not `CTSettings`**: both classes exist, `Settings` is the
   global element and extends the type, and rule 2 of 14.2 picks the element. Section 6.1's name
   list is unaffected — `CTSettings` is still there and is still what `Settings` extends.
